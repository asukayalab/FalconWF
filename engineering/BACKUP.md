# Backup & Restore — alpha.14 local foundation

This is same-installation local/staging recovery, not a production disaster-recovery certification. Product/FP alpha.14; FT remains alpha.6. Local queue, retention/protection, daily/weekly schedule and selected-attachment UI are implemented. Manual process-death journal resolution and plugin/theme bootstrap rescue are implemented locally. Cloud transport and production host certification remain pending.

## Ownership and boundaries

Backup/Manager owns archive/inventory/validation/revision/recovery. Dashboard owns human admin capability fwf_manage_system and dedicated action nonces. No REST/AI backup tools. An eleventh screen under the existing Falcon WF menu supports component selection, local archive creation, authenticated download, computer ZIP upload, review and confirmed restore. ZIPs have no password/encryption.

FWF_BACKUP_DIR must exist, be writable and private mode0700, outside ABSPATH. ZIP files mode0600, UUID names; no public URL. Docker has a separate persistent volume at /fwf-backups; no backups/database/uploads/credentials enter Git or release artifacts. Server configuration, salts/API constants, account/usermeta tables and operational audit are excluded. Unknown third-party database tables/options may contain sensitive vendor data; do not claim generic secret redaction. Users/auth/session/application-passwords, role permissions, AI grants/connections/idempotency/budget and core/project update connections are not rewound. Current active_plugins/stylesheet/template/home/siteurl/cron/transients/locks/review candidates remain in place.

Components: database (site-prefix tables excluding account/usermeta/audit), media (uploads), plugins, themes, settings (allowlisted FWF design/SEO/identity/schema/modules and native identity/Reading). With database selected its options include the settings component; settings alone backs up the allowlist only. File components use actual roots, reject symlinks, omit .git/.env/wp-config.php/debug.log. All-uploads media-only creates an archive of bytes; choose database too for all native attachment records/metadata. Selected-media mode includes its own scoped native attachment records and cannot be combined with the whole database. Files restore as an overlay: extra files are preserved, not purged. WordPress core, server configuration and account recovery require separate host backups.

## Package and consistency

ZIP contains manifest.json, signature.txt, database.json (table index or settings-only values), rows/{table}.jsonl and files/{component}/{relative-path}. Manifest schema3; alpha.7 archives do not match current code/format. Manifest lists every payload's size/SHA256 and original file mode, site identity, WP/FP version and exclusions. HMAC using current site auth salt proves same-installation origin, not confidentiality. Changed URL/salts or code/WP version rejects restore. Schema comparison must match current tables; this is not cross-site migration or cross-version rollback.

No fixed64MiB files/32MiB DB/5000 files/50000 rows cap remains. Database export reads100 rows per batch into staging JSONL files, with base64 cells/null. ZIP payload checksum/restore uses streams; original file journals use disk copy. Manifest/table metadata and a database row still require memory, while file inventory grows with file count. Runtime memory/ZIP/disk capacity and host execution time remain finite; database capture and individual ZIP entries still require one PHP execution; archive batches persist between workers. This does not remove host timeout limits within one snapshot or one ZIP entry. Disk checks use estimated selected bytes with headroom and a32MiB reserve; restore checks inventory bytes. Browser imports additionally follow WordPress/PHP upload limits, shown in UI. This is not a guarantee of unlimited site size.

UI displays per-component pre-compression size (actual included file bytes; DB estimated base64/row overhead from data lengths), file counts and selected total. Settings are already included when database is selected and not counted twice. Database estimate may include preserved/volatile options and vary with encoding; final ZIP size is shown separately. Estimates are a snapshot, not a reservation against concurrent writes. InnoDB and no foreign keys required. Data stores base64 cell values/null rather than accepting SQL/DDL from an archive. Transactional consistent database read; file hashes rechecked after archive close. Backup requires a quiescent operational window: concurrent in-flight content/file writers can prevent a single common DB/files snapshot. Neither maintenance banner nor locks is a universal third-party write barrier. Scheduling/live-host quiescence remains pending.

## Persisted background jobs

Admin create queues a private job-{UUID} directory with0600 state.json in0700 directory. Manager is the single owner of queue/snapshot/archive/recovery; synchronous safety backups drive the same engine without scheduling. Each worker holds an exclusive OS flock backup lease, rechecks the requesting admin capability, exact site identity and code version, and atomically checkpoints state. The OS releases that lease on worker termination; it never steals a live process lease. Legacy option locks still need operator reconciliation. Local filesystem flock behavior is tested; shared/network filesystem hosting behavior remains unverified.

Queued/snapshot stage takes a consistent DB transaction and copies actual file bytes into private immutable staging, checking hashes before/after. Interrupted snapshot capture restarts from scratch; there is no transaction carried across requests. Packing reopens a ZIP, adds up to8 whole entries, closes it and records the cursor. A death between close and checkpoint may redo the last batch by replacing existing ZIP names. Missing partial archive restarts packing; invalid partial archive pauses and explicit retry rebuilds ZIP from staged snapshot. Live site edits after completed capture do not change archived staging. Final verification uses the same HMAC/hash/inventory validator as import/restore; final rename is recognized idempotently if a worker dies before recording completion. Backup no longer holds its DB transaction while ZIP compression runs.

Cron worker processes one stage/batch. WP-Cron is visit-driven; status polling does not certify reliable unattended execution. A server cron must be configured for a quiet site or DISABLE_WP_CRON installation. UI displays job stage/entry progress, human continue/retry/cancel and authenticated nonce-protected AJAX polling. Percentage/ETA is not guessed; entry counts do not imply equal work per entry. Cancellation discards only owned staging and leaves site content and completed ZIPs intact. Terminal job metadata remains private until archive deletion; retention cleans terminal metadata of pruned archives. Deactivation clears scheduled worker hooks while preserving staged data; manually continue after reactivation. Jobs from older code cannot run; cancel and start a new backup. This is a job runner, not periodic backup scheduling or cloud transport.

Snapshot/one ZIP entry/final verification can still exceed a hosting timeout; repeated timeouts at these boundaries require server limits/CLI support or later finer-grained processing. Restore remains synchronous with manual crash journal reconciliation. No auto-replay of an uncertain restore commit is introduced.

## Restore and failures

Review verifies exact inventory, dynamically memory-checked metadata, SHA256, HMAC, version/site, no encryption, symlinks, traversal, aliases, duplicates or unexpected entries. Per-user10-minute review transient records package hash and live DB/file revision. Apply rechecks both, requires explicit checkbox and local/staging writable policy, and creates a safety backup before writes. Shared updates lock prevents overlapping FWF updater. No theme/plugin activation is performed.

Files are journaled before replacement, temp-written then renamed; supported file mode restored. DB schema must match, tables replaced in an InnoDB transaction using validated column names/decoded cells and WP prepared inserts. Preserved option IDs are not overwritten. A handled failure rolls DB back and restores previous file bytes/modes; recovery failure retains private journal. Process-death journals are resolved manually through Recovery using a transaction commit proof and named database lease; an unfinished restore directory blocks new backups/restores. Unknown session changes remain blocked. SHORTINIT rescue skips normal plugins/themes, while core/config/database/drop-in repair still requires host support. Restore does not remove newly added files, restore DB AUTO_INCREMENT counters/ACLs/ownership, or certify third-party plugin hooks/host combinations.

## Archive cards, notes and deletion

Local means the server hosting this installation. FWF_BACKUP_DIR remains private outside WordPress; Download ZIP obtains a computer copy. Cards display site-timezone date/time first and UUID.zip(actual ZIP size) second, with grouped Download ZIP, Restore and Delete controls. Restore routes through the existing selected-file validator, revision review, explicit confirmation and safety archive.

Optional notes can accompany queue creation and be edited later per archive. Manager sanitizes plain text, limits to1000codepoints/4000bytes and stores non-autoload fwf_backup_note_UUID in the already protected fwf_backup_* operational namespace. Display escapes text and attribute contexts. Notes are retained through data/settings restore and are not part of archive payload/import; imported ZIP starts without a note. Cancelling an unfinished queue cleans its note. Job state remains separate from archive note metadata.

Delete first shows selected date, filename and size. Per-admin10minute review stores ID+SHA256; confirm endpoint requires its own nonce, capability, matching ID and explicit checkbox. Manager locks the same backup lease and rehashes selected ZIP; changed file, active job or pending restore journal prevents deletion. Archive deletion also cleans its note and terminal job metadata but leaves site content and other archives in place. Browser execution never performs permanent deletion without human action-time approval; HTTP/runtime fixtures delete only owned test archives in isolated local tests. Retention uses this manager boundary under the held backup lease, sharing guards and metadata cleanup.

## Retention and protection

Alpha.11 adds an opt-in policy: default disabled, initial limit5, accepted1–1000 ordinary archives. Save requires current policy revision and never deletes immediately. The retaining worker phase runs after final ZIP validation/rename. Oldest unprotected archives are deleted until the ordinary quota is reached; protected archives and the new ZIP are preserved. Unprotect changes eligibility only. Equal-time archives have no promised relative ordering. Failures before final validation do not trigger pruning; pruning guards stop on errors and report deferred cleanup without deleting the valid new archive.

Per-file fourth control toggles Lindungi backup ini/Lepas Perlindungan, with a lock indicator. Protected Delete is disabled and rejected at Manager level. Marker/policy/result are non-autoload operational options preserved through restore, not embedded in ZIP. Host operators can still remove files; protection is not ZIP encryption. Protected archives are additional to quota and consume space; UI shows total archive count/protected count/actual total ZIP size.

Synchronous safety backups do not prune while restore may still need the source. They can temporarily exceed quota; a later successful normal background backup enforces it. Background retaining checkpoint can resume after interruption; deletion is idempotent by listing remaining files. This retention phase alone adds no schedule, cloud integration or restore crash certification. See BACKUP-ROADMAP.md.

## Calendar scheduling (alpha.12)

Scheduler is the sole calendar/cron policy owner, while Manager remains the only archive engine. Daily/weekly choice, selected components, weekday and HH:MM are saved with system capability/nonce/revision under a private schedule flock. Disabled by default. Save captures the current WordPress timezone; future UTC event times are calculated in calendar days, preserving chosen clock time across normal DST transitions (a nonexistent local time follows PHP timezone normalization). Change site timezone then save schedule again to apply it.

Use one single WP-Cron event with generation+due arguments. Reconcile creates a missing event and never replaces an existing due event simply because visits were delayed. A late slot queues one backup and calculates the next future calendar slot; no catchup flood. Durable claim and pending record share one state write before queue creation, so duplicate/stale callback cannot replay an executed slot. Bootstrap/save reconciles a pending record missing from history, including death immediately after state commit. An interruption between claim and queue/result persistence remains a starting/unknown record requiring operator review. Configuration save failures restore prior policy/state and attempt to rearm it; cron failure is visible rather than silently claimed successful.

A running backup skips that period with a reason, rather than stacking another job. Lock contention also skips; other queue failures are recorded. Original schedule admin permission is rechecked; revocation blocks future scheduling until an admin saves again. Manager continues rechecking job owner. Completed periodic ZIPs invoke the same retention stage and protection guards as manual background jobs. Narrow terminal notification records done/failed/cancelled and warnings; read-only UI reconciliation shows actual job result if the notification was blocked. Keep20terminal records plus pending/unknown records; history/options are operational and preserved by data restore.

Deactivation pauses periodic scheduling and clears job/periodic cron hooks while retaining all data. Activation rearms saved periodic schedule; old incomplete jobs still require manual continue/cancel. No theme switch or purge. Docker worker invokes only due scheduled events via wp cron event run fwf_backup_scheduled --due-now, plus existing backup steps. WordPress visit-driven scheduling is documented at https://developer.wordpress.org/reference/functions/wp_schedule_single_event/ . Server cron setup and host timing/resource certification are still pending; this is not a cloud transport or a production recovery guarantee.

## Selected media and reports (alpha.13)

Manual and periodic backup forms share native WordPress Media Library selection and one MediaSelection schema owner. AJAX estimate requires system capability and dedicated nonce; IDs are canonical positive unique integers. Selected scope requires media and excludes whole-site database; other selected components retain their existing semantics. Queue checkpoints and signed schema3 manifest store the root IDs. Scheduler stores those IDs, not a dynamic category/query; a later missing selected attachment or declared file causes a reported failure.

Follow canonical `_thumbnail_id` attachment dependencies (including PDF cover), original attached file, metadata sizes/original_image and attachment edit-backup sizes. Include exact native posts rows and allowlisted metadata `_wp_attached_file`, `_wp_attachment_metadata`, `_wp_attachment_backup_sizes`, `_wp_attachment_image_alt`, `_thumbnail_id`. Canonical metadata decode rejects objects and bounded-depth/recursive serialized values. Require every declared file and reject symlinks, traversal, duplicate metadata, ID collisions and file paths that are also primary files of attachments outside the selection. Exact ZIP file inventory must match declared metadata closure. Selection estimate includes attachment JSON plus uncompressed file bytes; compression and safety snapshot size are separate.

Restore upserts original attachment IDs and replaces only those canonical metadata keys within the existing database transaction/file journal. Unselected posts/files and custom third-party metadata remain unchanged. Attachment author and external parent must still exist; selected attachment parents can be restored together. Review rejects incompatible live ID/GUID/path ownership before creating safety backup. Live revision remains conservative across database/uploads, so concurrent unrelated edits invalidate review. Safety snapshot uses full supported database/uploads through the same Manager engine; it can be much larger than the selected archive. No attachment deletion, theme activation, account restore or arbitrary SQL from ZIP. Custom plugin metadata recovery and cross-site ID remapping are unsupported. Older FP/schema archives remain downloadable but require their exact compatible runtime for restore.

## Interrupted restore and operator rescue (alpha.14)

The same Recovery class owns runtime handled-failure undo and manual recovery. Each restore persists a signed private state and fsynced undo copy before replacing a target. A database connection named lock complements the backup filesystem flock. The commit marker is inserted on the original connection inside the same InnoDB transaction as restored data. A fresh leased connection reads its exact proof: committed keeps restored files/data; rolled-back restores only file undo. No backup SQL is replayed. A recorded connection change without a committed proof is uncertain and cannot be resolved through this action; operator must inspect DB/safety backup.

Dashboard Backup & Restore → Pemulihan restore terputus offers per-journal review then explicit confirmation. Review lasts10minutes and is tied to state, commit proof, current target bytes/modes and lock state. HMAC/path/root/symlink/undo-copy checks and newer target edits prevent unsafe writes. Only the journal's original update lock may be released. Pending journal blocks new backups; synchronous failures use the same resolver. Terminal checkpoint is written before deleting proof/lock, then the journal is atomically renamed to completed-restore-UUID before private cleanup. A failure during retired cleanup leaves operator-owned private files without replaying completed content writes; the same dashboard/CLI review identifies cleanup_only and removes remaining private slots without touching newer live file bytes. A damaged or empty state still requires direct operator inspection.

Technical operator procedure (not the deferred full FWF0.1 manual): stop site writes/traffic, verify original PHP writer has ended, identify the UUID from the private restore-UUID folder, and use the trusted current installer code. Run from the server's PHP CLI:

```sh
php /path/to/trusted/falcon-wf/rescue.php --root=/path/to/wordpress --inspect=JOURNAL_UUID
php /path/to/trusted/falcon-wf/rescue.php --root=/path/to/wordpress --apply=JOURNAL_UUID --review=SHA256_FROM_INSPECT --confirm
```

The trusted directory must include rescue.php, autoload.php and matching src classes (extract the verified installer if installed code is damaged). Inspect does not replay/undo files. Check decision, affected-file count and safety archive ID before the second command; never guess the hash. CLI uses server filesystem authority and refuses HTTP execution, multisite and apply outside local/staging writable. Current wp-config must point to the same private directory with its0600 `.recovery-key`; do not rotate/delete that key while journals exist or export it to Git/ZIP.

SHORTINIT still needs functional WordPress core/config/database and any DB/object-cache drop-ins that load before its cutoff. After a proved commit, rescue deliberately retains the restored code: it cannot promise a faulty committed plugin becomes functional. Operator may need verified code repair or a separately reviewed complete safety restore, keeping database/code consistent. Lost DB session, damaged proof/key/journal, DB failover/replica changes, legacy journal and host power loss are not automatically replayed. Existing exact-site/FP/WP/archive compatibility and third-party exclusions remain. No automatic theme switch or purge.
